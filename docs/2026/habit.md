## 一、代码编写习惯

### 1. 代码风格与可读性
- **遵循命名规范**：变量、函数、类使用有意义的名称，避免 `a`、`b`、`tmp` 等无意义命名
- **保持代码简洁**：一个函数只做一件事，遵循单一职责原则
- **适当添加注释**：解释"为什么"而非"是什么"，复杂逻辑必须注释
- **统一代码风格**：遵循团队或语言的代码规范（如 Java 的 Google Style）

### 2. 代码组织
- **合理的项目结构**：按功能或模块划分目录
- **避免过长文件**：单文件超过 500 行考虑拆分
- **减少重复代码**：遇到重复代码及时抽取公共方法

## 二、版本控制习惯

### 1. 提交规范
- **频繁小提交**：每完成一个小功能就提交，避免大而全的提交。 这个对于我们的项目需要评估一下。
- **清晰的提交信息**：格式如 `[类型] 简短描述`，例如：
  - `feat: 新增用户登录功能`
  - `fix: 修复计算错误`
  - `refactor: 重构数据查询逻辑`
- **提交前检查**：确认不提交敏感信息、临时文件、IDE 配置、生成的文件等
```
# <类型>[影响范围]: <主题>
# |<----  建议不超过50个字符  ---->|

# [详细描述]
# |<----  每行不超过72个字符  ---->|

# [结尾，一般是写一点关联的缺陷或者是工单，比如是禅道的工单编号(s)]
# 示例:
# Closes #123
# BREAKING CHANGE: 描述破坏性变更

# 类型说明:
# feat: 新功能
# fix/bug: 修复bug
# docs: 文档
# style: 格式
# refactor: 重构
# perf: 性能优化
# test: 测试
# chore: 构建/工具
# ci: CI/CD
# revert: 回滚
```

### 2. 分支管理
- **功能分支开发**：新功能在独立分支开发，完成后再合并
- **及时同步主分支**：定期拉取最新代码，减少合并冲突

## 三、文档与注释习惯

### 1. 项目文档
- **README 必写**：项目介绍、安装步骤、使用方法
- **API 文档**：接口必须有说明、参数、返回值、示例
- **更新日志**：记录版本变更内容

### 2. 代码注释
```java
/**
 * 计算两个日期之间的天数差
 * @param startDate 开始日期
 * @param endDate 结束日期
 * @return 天数差，负数表示endDate在startDate之前
 */
public int calculateDaysBetween(Date startDate, Date endDate) {
    // 业务逻辑...
}
```

## 四、测试习惯

### 1. 单元测试
- **先写测试再写代码**：TDD 开发模式
- **边界条件测试**：空值、边界值、异常情况
- **保持测试独立**：测试之间不相互依赖

### 2. 自测习惯
- **本地充分测试**：提交前本地跑一遍测试
- **多场景验证**：正常流程 + 异常流程 + 边界情况

## 五、安全意识习惯

### 1. 敏感信息保护
- **不硬编码密码**：数据库密码、API Key 等放配置文件或环境变量
- **配置文件不提交**：`.gitignore` 排除敏感配置
- **日志脱敏**：不打印用户密码、身份证等敏感信息

### 2. 输入校验
- **永远不信任用户输入**：前后端都要校验
- **防范 SQL 注入**：使用参数化查询，不用字符串拼接
- **防范 XSS 攻击**：输出时进行转义

## 六、性能与优化习惯

### 1. 数据库操作
- **避免 N+1 查询**：使用 JOIN 或批量查询
- **合理使用索引**：查询字段建索引，但不过度索引
- **大事务拆分**：长事务影响性能，尽量拆小

### 2. 代码性能
- **避免循环内查询数据库**：提前查询，内存中处理
- **合理使用缓存**：频繁访问且变化少的数据加缓存
- **及时释放资源**：连接、流、文件用完关闭

## 七、异常处理习惯

### 1. 异常捕获
```java
// ❌ 不好：捕获后什么都不做
try {
    doSomething();
} catch (Exception e) {
}

// ✅ 好：记录日志并处理
try {
    doSomething();
} catch (Exception e) {
    log.error("操作失败: {}", e.getMessage(), e);
    throw new BusinessException("操作失败，请联系管理员");
}
```

### 2. 异常分类
- **区分业务异常和系统异常**：业务异常用户可理解，系统异常需要技术处理
- **异常信息友好**：用户看到的错误信息要易懂

## 八、日常开发习惯

### 1. 开始工作前
- 拉取最新代码
- 查看待办事项和 Bug 列表
- 了解今天要做的任务

### 2. 编码过程中
- 先思考再动手，画图理清逻辑
- 一边写一边调试，不要写完一大堆再调试
- 遇到问题记录下来，事后总结

### 3. 完成工作后
- 代码自审一遍
- 更新相关文档
- 提交前本地完整测试
